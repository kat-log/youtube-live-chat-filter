## レベル1 — データが失われる／機能が黙って止まる

### #1 dom-chat.js が無関係なフレームに注入され、そこで永久ポーリングする

**箇所**: `SW:1375-1378` と `dom-chat:50-56`

```js
// SW 1375
await chrome.scripting.executeScript({
  target: { tabId: tabId, allFrames: true },   // <- URLフィルタが無い
  files: ['content/dom-chat.js']
});
```

```js
// dom-chat 50
function attachObserver() {
  const itemList = document.querySelector('yt-live-chat-item-list-renderer #items');
  if (!itemList) { setTimeout(attachObserver, 500); return; }   // <- 回数上限が無い
```

`allFrames: true` に URL 条件が無いため、`host_permissions`（`*://*.youtube.com/*`）に
合致するフレームすべてに注入される。watch ページの**トップフレーム**もそのひとつだが、
そこに `yt-live-chat-item-list-renderer #items` は存在しない。
結果 `attachObserver` が**回数上限なしで 500ms ごとに `querySelector` を叩き続ける**。
セッションが終わるまで止まらない。余分な `chrome.runtime.onMessage` リスナー (`dom-chat:58`) も残る。

manifest の自動注入 (`manifest.json:22-26`) は `live_chat*` 限定なので問題ない。
**SW からの明示注入だけが原因。**

**確認方法**: watch ページの DevTools > Performance を記録し、500ms 周期のタイマーを探す。

### #2 MutationObserver を張り直せないので、YouTube が `#items` を作り直すと無言で止まる

**箇所**: `dom-chat:50-56`

```js
  doInitialSweep();
  new MutationObserver(handleMutations).observe(itemList, { childList: true });
```

observer を変数に受けていないため `disconnect()` できず、張り直す経路も無い。
`attachObserver` は「`#items` が見つからない間だけ」再試行するので、
**一度張ったあとに `#items` が差し替わると復帰しない**。

再現しうる操作: YouTube 側の「上位のチャット ↔ チャット」切替、チャットのリロード、
YouTube の A/B テストによる DOM 変更。

`childList: true` のみで `subtree` が無いため、YouTube がラッパー要素を1枚挟むだけでも同様に壊れる。

**症状はつねに「コメントが来なくなる」だけで、ログもバッジも何も変わらない。**
現状これを利用者が切り分ける手段が無い。

### #3 popup の重複判定が `id` を見ておらず、連投コメントを消す

**箇所**: `popup:1312-1320`（原因は `popup:1335-1385`）

```js
const uniqueComments = formattedComments.filter(newComment => {
    return !this.comments.some(existingComment =>
        existingComment.message === newComment.message &&
        existingComment.displayName === newComment.displayName &&
        existingComment.publishedAt === newComment.publishedAt &&
        existingComment.amountText === newComment.amountText &&
        existingComment.eventText === newComment.eventText
    );
});
```

`formatComment` (`popup:1335`) が返すオブジェクトに **`id` が含まれていない**ため、
本文5フィールドの一致で代用している。

DOMモードの過去分コメントは `parseTimestampText` (`dom-chat:274`) 由来で
**時刻が分単位**（秒は 0 に丸められる。`dom-chat.test.js` がこれを固定している）。
したがって**同じ人が同じ分に同じ本文を2回投げると、2件目が消える**。
モデレーターの「8888」「www」のような短い連投で普通に起きる。

計算量も `O(N x M)`。`this.comments` の上限は 10,000 件 (`popup:1326`) なので、
1バッチ20件なら最大20万回、それぞれ最大5フィールドの文字列比較。→ #22 と同根。

**箇所**: `SW:1423-1428`

### #5 `handleDomChatMessages` が直列化されておらず、動画切替中のバッチが消える

**箇所**: `SW:1393-1457`（特に `1396`, `1411`, `1435`）と `SW:1344`

```js
async function handleDomChatMessages(messages, sender = null) {
  await ensureStateRestored();                             // 1396: await
  ...
  if (/* 動画が変わっていたら */) {
    await startDomMonitoring(senderTabId, senderVideoId);  // 1411: await（内部でも複数 await）
  }
  ...
  monitoringState.commentsHistory.push(...newMessages);    // 1435
```

`chrome.runtime.onMessage` (`SW:1004-1009`) は `sendResponse` を即返して
処理を切り離すため、**バッチが直列化されない**。

バッチAが `startDomMonitoring` の中にいる間にバッチBが入ると、
Bは**古い** `monitoringState` に対してガード (`SW:1414`) を通過し、
古い `commentsHistory` 配列と古い `processedMessageIds` に書き込む。
その後Aの `startDomMonitoring` が `monitoringState = {...}` (`SW:1344`) を実行し、
**Bのコメントは参照ごと捨てられる。**

同じ再入問題は `startPollingLoop` にもある。`stopBackgroundMonitoring` (`SW:1150-1153`) は
タイマーを消せるが**実行中の `fetch` は止められず**、その `.then` が `SW:1268` で
タイマーを張り直すため、**ポーリングループが二重に走る**（quota 消費も倍）。

世代番号（epoch）に相当するものがコード中に一切無いのが根本。

### #9 コメントIDが32bitハッシュで、長時間配信で衝突して消える

**箇所**: `dom-chat:249-270`

```js
let key = displayName + SEP + detail.message + SEP + timestampText;
if (kind !== 'text') key += SEP + kind + SEP + (detail.amountText||'') + SEP + (detail.eventText||'');

const hash = key.split('').reduce((a, c) => (Math.imul(31, a) + c.charCodeAt(0)) | 0, 0);
const occurrence = occurrenceByKey.get(key) || 0;
const id = `dom_${hash}_${occurrence}`;
```

（実際の区切りは U+0000。ここでは `SEP` と表記した）

`| 0` により 32bit に丸められる。誕生日問題から、**異なるキーが約65,000通で衝突確率50%**。
賑わった配信の数時間で到達しうる。

`occurrence` は**同一キーの重複**を区別するためのもので、
**異なるキーのハッシュ衝突は救えない**（どちらも occurrence 0 から始まる）。
衝突した2件目は SW の `processedMessageIds` (`SW:1424`) に黙って落とされる。

さらに `timestampText` が分単位なので、キーの多様性が想定より低く衝突窓が広い。

**テストは無い。** ID生成は `dom-chat.test.js` の「同じ行がもう一度流れてきても二重に送らない」で
間接的に触れられるだけで、衝突は検証されていない。

### 実装時に踏んではいけない地雷

両 content script は二重注入ガードのため `if (guard) { } else { ... }` のブロックで包まれている
(`cs:5-6`/`cs:662`, `dom-chat:2-3`/`dom-chat:338`)。
ハーネスは **Annex B の sloppy モード関数巻き上げ**（ブロック内の関数宣言がスクリプトスコープに漏れる挙動）を
使って内部関数に到達している。

**`'use strict'` を足すか、ES モジュールに変換すると、
`h.domChat.<関数名>` がすべて `undefined` になり、テストが原因不明の `TypeError` で全滅する。**

モジュール構造を近代化する変更をするなら、ハーネスの露出方式ごと作り直す必要がある。
